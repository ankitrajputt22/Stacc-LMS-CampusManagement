# Stacc Repository Instructions

- Stacc uses MySQL. Treat older references to PostgreSQL as outdated unless a current phase explicitly changes this decision.
- Use a modular-monolith architecture with clear domain boundaries.
- Place backend code inside the correct Stacc module. Keep `common` small, and avoid cross-module dependencies without a clear need.
- The frontend uses React and TypeScript; the backend uses Java and Spring Boot.
- Work only on the currently requested development phase. Do not implement future features early.
- Inspect the repository before editing and preserve existing working functionality.
- Do not refactor unrelated code without a clear phase-related reason.
- Never hard-code credentials or secrets. Use environment configuration instead.
- Settings come from environment variables listed in `docs/configuration.md`. Development has safe `localhost` defaults; the `prod` profile has none for hosts and names, logs JSON, closes the API description, and `ProductionSettingsCheck` refuses unsafe combinations (root database user, test password or `dev-seed`, empty storage keys, non-https origins, AI without a token). A new setting gets a checked `@ConfigurationProperties` record, an `.env.example` placeholder, and a line in that doc.
- Enforce permissions on the backend; frontend visibility is not a security boundary.
- Never store plaintext passwords. Store only password hashes, and never log or expose raw passwords or hashes.
- Hash and check passwords only with the shared `PasswordEncoder`. Do not compare password strings yourself or write custom hashing code.
- Keep `UserAccount` separate from student and faculty profile data.
- Names, the preferred name, contact details, and the official photo live on `PersonProfile` (`identity.person`), at most one per account. The college sets the full name, email, and photo; the person may change only the preferred name and phone. Contact details are shown only to the person (and later to staff with a permission); never put names or contact details in tokens, URLs, or logs. See `docs/person-profiles.md`.
- Do not expose JPA entities such as `UserAccount` directly through APIs.
- Disable an account through its status. Do not delete accounts just to remove access.
- Roles are assigned by the college through the backend. Users never choose their own role.
- The roles are `STUDENT`, `FACULTY`, `ADMIN`, and the staff roles `HOD`, `WARDEN`, `SECURITY`, `MAINTENANCE`, `LIBRARIAN`, and `PLACEMENT_OFFICER` (`RoleName`, `ACCOUNT_ROLES`, always in that order). A staff role holds only the own-profile permissions until its feature adds more; never give it access ahead of its phase. See `docs/account-roles.md`.
- An account can hold several roles. Do not assume it has only one.
- `Role` rows are shared reference data. Never create or delete them as a side effect of changing an account.
- Permission codes use `UPPERCASE_WITH_UNDERSCORES`. Add a permission only when a real feature needs it, through a migration.
- A role can hold several permissions, and a permission can be shared by several roles. Assign a permission to roles only when its protected feature exists.
- Roles and permissions are shared reference data. Do not use cascading deletes on their relationships.
- Users never grant themselves roles or permissions.
- Sensitive actions are recorded through the one append-only `audit.AuditService.record`, in the same transaction as the change, with the actor from the token and short plain-text details that never hold passwords, hashes, tokens, names, or contact details. Never update or delete `audit_events` or add a write route; admins read it at `/api/v1/admin/audit-events` (`ADMIN` with `AUDIT_LOG_VIEW`) and `/admin/audit`. See `docs/audit-log.md`.
- Admins manage accounts only through `identity.admin.UserAdminService` (`/api/v1/admin/users`, `ADMIN` with `USER_VIEW` and, for changes, `USER_MANAGE`): create with a policy-checked temporary password and the profiles the roles need, correct official name and email, set status and roles (a real change ends the account's sessions), issue temporary passwords. Login IDs never change; nothing is deleted; an admin never disables their own account or removes their own `ADMIN` role. Bulk CSV import (`UserImportService`, `POST /api/v1/admin/users/import`) checks every row first, creates all accounts or none through the same creation path, never reads a password from the file, and hashes the one admin-typed temporary password once. See `docs/user-management.md`.
- Keep all Spring Security settings in the shared `SecurityConfig`. Do not add separate security filter chains for individual modules without a real need.
- Every route under `/api/` requires authentication by default. Make a route public only deliberately, with a clear reason, by listing it in `SecurityConfig`. The login stays public.
- Public routes are versioned under `/api/v1/`; the security and CORS rules cover all of `/api/`. The frontend's `apiClient` adds the version (`API_VERSION`), so `VITE_API_BASE_URL` and API modules never contain it. The internal AI service lives under `/internal/v1/`. A breaking change gets a new version beside the old one, never a silent change.
- Check roles with `hasRole` or `hasAnyRole` and permissions with `hasAuthority` or `hasAnyAuthority`. Add a rule only when a real feature needs it.
- A permission's code is its authority name. Never add `ROLE_`, `SCOPE_`, or any other prefix to it, and never start a permission code with `ROLE_`.
- There is no role hierarchy and no automatic admin pass, for roles or for permissions. Do not add either without an explicit design decision.
- Do not build a custom permission engine or guess permission constants. Use Spring Security's checks.
- Do not use Spring's generated login page or HTTP Basic, and never add built-in, demo, or hard-coded users. Authentication must use `UserAccount`.
- Sign-in goes through the shared `AuthenticationManager`, with `loginId` as the identifier. Roles map to `ROLE_*` authorities, and permission codes are used as authorities unchanged.
- There is one central college login (`POST /api/v1/auth/login`) and no public signup. The login request never carries a role.
- Failed logins always return the same generic 401 message. Never reveal whether a login ID exists, and never log passwords or login requests.
- Repeated failures slow down further tries through `auth.throttle.SignInThrottleService` (per login ID and per address, growing delays, 429 before the password is checked, unknown IDs treated like real ones). Never lock accounts, never store a login ID or address in clear (hashes only), and trust `X-Real-IP` only when `STACC_SIGN_IN_TRUST_PROXY` says the backend sits behind Stacc's own proxy.
- For an expected failure with a specific status, throw `ApiException` with a client-safe message.
- Every request has one ID (`RequestIdFilter`, header `X-Request-ID`): in every error body as `requestId`, in each log line, and passed on to the AI service. Never put personal data in it or log request bodies beside it. Only Actuator's health endpoint is exposed; readiness needs only the database, and health shows statuses, never details. See `docs/operations.md`.
- Every sign-in is a row in `user_sessions` (`auth.session.SessionService`), started only by the login. Tokens are created only by `AccessTokenService`, carry the session ID as `sid`, and last as long as the session can; every request is accepted only while its session is open and its account `ACTIVE` (checked once per request). Signing out, signing out everywhere, idleness, and disabling an account end sessions; never reopen one. Never put passwords, hashes, or private data in token claims.
- Passwords change only through `auth.password.PasswordService`, checked by `PasswordPolicy` (10 to 128 characters, no login ID, not common, not the current one). Changing one's own password (`POST /api/v1/me/password`) needs the current password and ends every other session of the account. A temporary password sets `password_change_required`, expires (then the login answers the generic 401), and ends every session; while a change is required the session has no authorities, so only routes that need a signed-in session alone work. See `docs/password-security.md`.
- Never hard-code, log, or expose the JWT signing secret, and never log tokens or put them in a response body. Do not add refresh tokens.
- Browsers carry the token only in the `STACC_SESSION` cookie (HttpOnly, SameSite=Lax, path `/api`, Secure in production), read by `SessionCookieAuthenticationFilter` after the CSRF check; API clients and tests may send it as `Authorization: Bearer`. Never accept a token from a URL. A change signed in by the cookie must pass CSRF (the `XSRF-TOKEN` cookie copied into `X-XSRF-TOKEN`); keep CSRF on, and never let Spring rotate the XSRF token per request. See `docs/authentication.md`.
- Token authorities are used unchanged, with no `SCOPE_` prefix. Do not query the database on every token request unless a later phase explicitly requires it.
- Keep frontend and backend API contracts consistent.
- Frontend API calls use the shared `apiClient` in `frontend/src/api/apiClient.ts`. Do not hard-code backend URLs in components or pages.
- Pages load data with `useApiQuery` and keys from `src/api/queryKeys.ts` (TanStack Query, one shared cache). Do not add polling or refetch on focus, and keep the cache cleared when a session ends or starts. Existing `useApiRequest` pages move over when they are redesigned.
- Do not put secrets in `VITE_` variables; they are public in the built frontend.
- Add feature API logic only when that feature is implemented.
- Use the shared API error format and Jakarta Validation for request DTOs. Do not expose stack traces or internal database errors, and do not create module-specific error formats.
- Keep new REST APIs visible in OpenAPI with simple, useful descriptions. Do not create fake endpoints for Swagger, and do not treat API documentation as an authorization control.
- Use Canvas LMS as a UX reference without copying its branding, assets, or exact design.
- Maintain a coherent Stacc identity across the UI. Google Stitch may provide approved design references.
- Frontend pages reuse the shared `AppLayout`. Do not create separate global navigation for each module.
- Reuse `LoadingState`, `EmptyState`, and `ErrorState` for page states.
- Build pages from the shared components in `frontend/src/ui` (`PageHeader`, `Card`, `Button`, `ButtonLink`, `TextField`, `TextAreaField`, `SelectField`, `Badge`, `Alert`, `LinkTabs`, `Tabs`, `DataTable`, `Pagination`, `Timeline` for every history or step list) and the class lists in `ui/styles.ts`, instead of writing new class lists per page. See `docs/ui-design.md`.
- Avoid generic dashboard-template styling such as heavy gradients, glass effects, glows, and decorative animation.
- App-wide backend tests extend `DatabaseFreeApiTest` and run without a database. When a new service needs repositories, list them there as stand-ins, or those tests cannot start.
- Tests that need real MySQL (migrations, constraints, row locks, races) extend `MySqlIntegrationTest`, are named `*MySqlIT`, and run in `mvn verify` on a throwaway Testcontainers MySQL seeded with the demo data. Each works on demo records no other test changes. Every new row-lock or capacity rule gets one, using `Concurrently.run`. See `docs/testing.md`.
- Frontend unit tests use Vitest and React Testing Library (`npm test`), sit next to the code as `*.test.ts(x)`, find elements by role and accessible name, and never call a real server. Add them with every phase that changes frontend rules or shared components. See `docs/testing.md`.
- End-to-end tests use Playwright in `e2e/` against the whole Docker stack, started by `e2e/stack.sh` as the separate Compose project `stacc-e2e` with generated passwords outside the repository; never point them at the `stacc` project or a real database. Every new user-facing flow adds or extends a journey; journeys find elements by role and name and are never retried. See `docs/testing.md`.
- Keep commit messages simple and human-readable.
- GitHub Actions (`.github/workflows/ci.yml`) runs the backend tests, the frontend lint and build, and the AI service lint and tests. Merge a phase only after they pass on its branch, and never skip or disable a failing check. CI uses no secrets. See `docs/continuous-integration.md`.

## Academic Data

- Academic master data belongs in the `academic` module. The ERP side is the source of truth for academic structure and enrollment.
- Keep academic history. Make a record inactive instead of deleting it, and do not use cascading deletes on academic data.
- Department codes are unique and stored in uppercase.
- A program belongs to exactly one department. Its code and name are unique within that department, never across the college.
- An academic session is college-wide. Do not attach it directly to a department or a program, and do not assume it lasts exactly one year. Use `LocalDate` and `DATE` for its boundaries.
- A semester connects one program and one academic session. Its identity is program, session, and semester number together; the number alone is never unique.
- A course is permanent catalog data with a college-wide unique code and one owning department. It never belongs directly to a program, a semester, or a session.
- Use `BigDecimal` and `DECIMAL` for academic credits, never `double` or `float`.
- A course offering links one course to one semester, for the whole semester or for one active section of it, and a course appears at most once per semester and section, never both to the whole semester and per section. Do not copy the program, session, department, or the course's code, name, or credits onto it. Its capacity and registration status are enforced by student self-registration, and its capacity also by admin course enrollment.
- Sections, teaching assignments, timetables, and enrollment are separate concepts. Do not fold them into the course offering.
- `StudentProfile` belongs in the `identity` module. The student ID is the account's `loginId`; do not store it, the student's name, or the department on the profile.
- Never store a current semester or current session on `StudentProfile`. `admissionSession` is the session of original admission only. Ongoing participation comes from ERP enrollment, and a profile alone must not grant LMS access.
- A student's roll number is optional, uppercase, and unique on `StudentProfile`; the student ID stays the login ID. Admins correct roll numbers, profile statuses, and a faculty member's primary department only through `AcademicProfileAdminService` (`ACADEMIC_PROFILE_VIEW`/`_MANAGE`), never accounts, names, contact details, programs, or enrollments. `GET /api/v1/academic/me` reads one's own profile from the token, for every role held, with only published results; where a student studies now is worked out from their latest `ENROLLED` semester enrollment.
- `FacultyProfile` belongs in the `identity` module. The employee ID is the account's `loginId`; do not store it, the name, or other personal details on the profile. The future service that creates faculty profiles must check that the account holds `FACULTY`.
- `FacultyProfile.department` is the primary department only. It never limits or stands in for teaching responsibility, which must come from an explicit teaching assignment to a `CourseOffering`. Never map a faculty profile directly to `Course` or `CourseOffering`.
- Make a faculty profile inactive instead of deleting it. An account may hold both a student profile and a faculty profile.
- Teaching responsibility is the explicit `TeachingAssignment` entity in `academic.teaching`, from a faculty profile to a `CourseOffering`, never to a `Course` and never a plain many-to-many mapping. Several faculty may teach one offering; each faculty and offering pair exists once, with a role (`PRIMARY` or `CO_FACULTY`) and at most one active primary per offering, checked under the offering's row lock. Admins manage assignments only through `FacultyAssignmentService` (`FACULTY_ASSIGNMENT_VIEW`/`_MANAGE`): active faculty accounts holding `FACULTY`, open offerings, reactivation instead of a second row, and no delete.
- Responsibility is an explicit record, never a college-wide coordinator role. The head of a department is a `DepartmentHead` term in `academic.responsibility`: at most one active term per department (a unique generated column plus the department row lock), a new head ends the current term, and terms are never edited, deleted, or reopened. Who counts as head is worked out live by `DepartmentHeadResolver` (active term, `ACTIVE` account, still holding `HOD`); every later feature asks it instead of repeating the rule. Admins manage terms only through `DepartmentHeadService` (`DEPARTMENT_HEAD_VIEW`/`_MANAGE`, audited) at Academic Admin → People → Department Heads. See `docs/department-heads.md`.
- Do not copy the account, department, course, semester, program, or session onto a teaching assignment. Make it inactive instead of deleting it, and keep it free of any LMS reference.
- `SemesterEnrollment` is the official ERP record of semester participation. Do not copy the account, program, department, or session onto it, and keep its history instead of deleting it.
- Creating a semester enrollment must check that the student's program is the semester's program. Semester enrollment alone must not grant LMS course access, and course enrollment is a separate, explicit step.
- `CourseEnrollment` links a semester enrollment to a course offering. Do not copy the student, semester, program, session, or course onto it, and never auto-enroll a student in all offerings of a semester.
- Creating a course enrollment must check that the offering's semester is the semester enrollment's semester. ERP course enrollment is the source of truth for LMS course access.
- An enrollment status is not an academic result. Keep grades and results in their own models.
- Add each academic model only in its own phase, and add its permissions only together with the action they protect.

## Admin Academic Masters

- Admins manage `Department`, `Program`, `AcademicSession`, `Semester`, and `Course` in `academic.admin` under `/api/v1/admin/academic`. See `docs/admin-academic.md`.
- `Course` is permanent catalog data; `CourseOffering` is semester-specific. Offerings and enrollments have their own rules below. Do not manage profiles, teaching assignments, LMS courses, or accounts here.
- Use explicit request and response records; never bind or return entities. Requests carry no own ID: the route names the record. Parents are loaded on the server by ID and never created.
- Codes and parents are fixed after creation. Do not add soft-delete or version columns, and never add delete routes. Inactive or closed parents take no new children (409): departments for programs and courses, programs and closed sessions for semesters, courses and closed semesters for offerings.
- A `Section` (`academic.section`) belongs to one semester and never stores the program or session again. Students are placed only through their `ENROLLED` semester enrollment, into an active section of the same semester; lock the semester enrollment, then the section, then count `ENROLLED` students with a locking read before placing, so a capacity holds. Keep a section on ended enrollments as history, and deactivate sections instead of deleting them.
- Exactly one academic session may be current, enforced by a unique generated column and changed only through `AcademicSessionManagementService.makeCurrent` under a lock; a closed session is never current. Course types and degree types describe records and decide nothing until a phase gives them rules.
- A semester's registration period (`registrationOpensAt`, `registrationClosesAt`, `dropDeadline`) changes only through `PUT /api/v1/admin/academic/semesters/{id}/registration`: zoned moments stored in UTC, both ends or neither, closing after opening, a drop deadline only with a period and not before it opens, never on a closed semester. A program's optional `maxCreditsPerSemester` is `BigDecimal`/`DECIMAL(5,2)`, above 0 and at most 60; empty means no limit.
- Unique clashes answer 409 with a safe message, also when the database constraint catches a race. Never let SQL errors or constraint names reach a client.
- Reading needs `ADMIN` and `ACADEMIC_MASTER_VIEW`; changing also needs `ACADEMIC_MASTER_MANAGE`. `SecurityConfig` keeps `/api/v1/admin/**` to `ADMIN`. There is no admin pass outside these explicit rules.

## Admin Offerings and Enrollment

- Admins manage `CourseOffering`, `SemesterEnrollment`, and `CourseEnrollment` in `academic.admin` under `/api/v1/admin/academic/offerings` and `/api/v1/admin/academic/enrollments`. See `docs/admin-academic.md`.
- An offering is one course in one semester. Its course and semester never change after creation (409); only its status moves forward. Never add delete routes for offerings or enrollments.
- A semester enrollment is a student profile in a semester of the student's own program; a course enrollment is a semester enrollment in an offering of that same semester, and a section's offering takes only students placed in that section. Never allow a cross-semester or cross-section course enrollment, and never move a student out of a section while they are enrolled in its offerings.
- New enrollments always start `ENROLLED`; never take the status, the student, or the enrollment from a request body. `ENROLLED` may become `COMPLETED` or `WITHDRAWN` once (and a course enrollment `DROPPED`, only by the student); the same status changes nothing, and nothing reopens.
- A semester enrollment ends only after its course enrollments have ended. Never cascade statuses, and keep every enrollment as history.
- The student lookup is read-only and returns only profile ID, login ID, program, admission session, and profile status. Never create or edit accounts or profiles in enrollment APIs.
- Official course enrollment decides LMS access live (see LMS Data); enrolling or ending an enrollment touches no LMS table and never creates an `LmsCourse`.
- Offerings need `ADMIN` with `ACADEMIC_OFFERING_VIEW` and, to change, `ACADEMIC_OFFERING_MANAGE`; enrollments and rosters need `ADMIN` with `ACADEMIC_ENROLLMENT_VIEW` and, to change, `ACADEMIC_ENROLLMENT_MANAGE`.

## Course Registration

- Students register themselves in `academic.registration` (`docs/course-registration.md`): the student always comes from the access token, and registration creates an ordinary `CourseEnrollment`, never a separate registration record.
- Registration is all or nothing. Lock the student's semester enrollments, then the offerings, in ID order (admin enrollment uses the same order), then count `ENROLLED` places with a locking read, so a capacity is never exceeded. Check the registration status `OPEN`, the semester's period, the section, an earlier enrollment, the capacity, and the program's credit limit on the server every time.
- Dropping is only by the student, before the semester's drop deadline: the enrollment becomes `DROPPED` with `droppedAt` and is never deleted or reopened, and the same offering cannot be taken again. Admins complete or withdraw; they never set `DROPPED`.
- LMS access follows the enrollment live, so registering or dropping writes nothing on the LMS side.
- The admin enrollment monitor (`GET /api/v1/admin/academic/enrollments/course-enrollments`, `ADMIN` with `ACADEMIC_ENROLLMENT_VIEW`) filters and pages in one bounded query and only reads. Faculty class lists (`/api/v1/faculty/me/course-offerings`, `FACULTY` with `ENROLLED_STUDENTS_VIEW`) come only from `FacultyTeachingAccessService`; an offering not taught answers 404, and faculty never change enrollments. Neither shows contact details.
- The registration routes need `STUDENT` with `COURSE_REGISTRATION_VIEW`, `COURSE_REGISTER`, or `COURSE_DROP`. Do not add prerequisites, elective groups, waiting lists, or withdrawal approval without their own phase.

## Attendance

- Attendance (`academic.attendance`) belongs to `CourseOffering`, never to `Course` or `LmsCourse`, and must not depend on LMS data. See `docs/attendance.md`.
- Faculty attendance access comes from `FacultyTeachingAccessService`: an `ACTIVE` faculty profile with an `ACTIVE` teaching assignment for the offering. Find the offering from the stored session, never from the client. No admin pass.
- Creating a session snapshots the offering's currently `ENROLLED` course enrollments in the same transaction. Later enrollment changes never alter an existing roster, and faculty never add or remove students.
- Records start `UNMARKED`, never `ABSENT`. Saves name records by `attendanceRecordId` only, each once and from that session. The server sets `markedBy` and `markedAt`.
- Finalizing needs every record `PRESENT` or `ABSENT`. Students see only `FINALIZED` sessions, which can still be corrected between `PRESENT` and `ABSENT`, never back to `UNMARKED`.
- Never reopen or hard-delete sessions or records, and never store the attendance percentage. Do not add attendance thresholds, notifications, self check-in, QR, location, or biometrics without their own phase.
- Faculty routes need `FACULTY` and `ATTENDANCE_MANAGE`; `GET /api/v1/attendance/student/me` needs `STUDENT` and `ATTENDANCE_VIEW` and takes the student from the access token.

## Results

- An official result (`CourseResult` in `academic.result`) belongs to one `CourseEnrollment`, at most one each. Never store the student, account, course, offering, semester, program, or session on it again. See `docs/results.md`.
- It is official academic data, separate from `LmsSubmissionGrade`. Never calculate or synchronize it from LMS grades, assignments, or attendance, and never let it depend on an `LmsCourse`.
- Marks are `BigDecimal`/`DECIMAL(8,2)`: `0 <= marksObtained <= maxMarks`, `maxMarks > 0`, and the maximum is always given explicitly. The grade code is optional explicit data kept as entered; do not invent a grading scale.
- New results start `DRAFT`. Students see only `PUBLISHED` results. Published corrections stay published and keep the first `publishedAt`. Never delete, unpublish, or archive a result.
- New results need an `ENROLLED` or `COMPLETED` enrollment; existing results stay after any later enrollment change.
- Faculty routes need `FACULTY` and `ACADEMIC_RESULT_MANAGE` plus `FacultyTeachingAccessService` for the offering in the route, and the enrollment must belong to that offering. `GET /api/v1/results/student/me` needs `STUDENT` and `ACADEMIC_RESULT_VIEW` and takes the student from the access token. No admin pass.
- Do not add GPA, SGPA, CGPA, ranks, pass or fail, approval workflows, or revision history without their own phase.

## Academic Calendar

- Official calendar events (`AcademicCalendarEvent` in `academic.calendar`) are academic data, not LMS data. Each needs one `AcademicSession` and may name one `Semester`, which must belong to that same session; the server checks it. See `docs/academic-calendar.md`.
- Events are date-based: `LocalDate` start and end, the end included and never before the start. Categories are `ACADEMIC`, `HOLIDAY`, `EXAM`, `REGISTRATION`, and `OTHER`, stored as text; there is no assignment category.
- New events start `DRAFT`. Publishing sets `publishedAt` once; cancelling sets `cancelledAt` and keeps `publishedAt`. Both are idempotent, a cancelled event cannot be published or edited, and there is no restore and no hard delete. After the first publication the session and semester never change (409).
- Users see `PUBLISHED` events and `CANCELLED` ones that were published first, marked as cancelled; drafts never leak. Students get the events of their own `ENROLLED` or `COMPLETED` semester enrollments, faculty those of semesters they actively teach (no `LmsCourse` needed), each with the session-wide events of those sessions, and admins every visible event.
- Assignment deadlines always come from `LmsAssignment.dueAt` at read time; never copy them into calendar tables. Students get published deadlines of courses `LmsStudentCourseQueryService` lists, faculty draft and published ones of courses `LmsFacultyCourseQueryService` lists. Do not repeat or loosen those rules.
- `GET /api/v1/calendar/me` (the read-only `calendar` module) needs `ACADEMIC_CALENDAR_VIEW` with `STUDENT`, `FACULTY`, or `ADMIN`, takes the caller from the access token, and gives every role the account holds its part; never use `roles[0]`. `from` and `to` are dates at most 366 days apart; `timeZone` is a validated IANA zone that only maps days to deadline moments and decides no access.
- Admin event routes under `/api/v1/admin/academic/calendar/events` need `ADMIN` with `ACADEMIC_CALENDAR_VIEW` and, to change, `ACADEMIC_CALENDAR_MANAGE`. Students and faculty never create events.
- Publishing an event, or cancelling a published one, notifies its viewers once through the Inbox; a draft or a repeat notifies nobody. Do not add recurring events, reminders, email or push, personal calendars, bookings, timetables, attachments, or calendar import or export without their own phase.

## LMS Data

- LMS data belongs in the `lms` module. An ERP `CourseOffering` and an LMS `LmsCourse` are different concepts; do not put LMS state on the course offering.
- One course offering maps to at most one `LmsCourse`.
- Do not copy the course, program, semester, academic session, or department onto `LmsCourse`.
- ERP `CourseEnrollment` remains the source of truth for official LMS student access. A `PUBLISHED` LMS course alone grants no student access.
- Archive an LMS course instead of deleting it, so its history is kept.
- The `lms` module may use academic data. Academic models must never refer to LMS models.
- ERP `CourseEnrollment` is the source of truth for official student course participation, and student LMS access is worked out live from it and the course's state (roadmap decision 5). There is no student membership copy: never add one, a sync job, or a provisioning step. The old `lms_student_memberships` table is kept only as history; nothing reads or writes it.
- Student access to an LMS course is decided on the backend by `LmsStudentAccessService`, from the signed-in account's ID. Hiding things in the frontend is not security, and an ID sent by the client never says who the caller is.
- Current student access needs all of: an `ACTIVE` student profile, an `ENROLLED` semester enrollment and course enrollment, a `PUBLISHED` LMS course, and the same course offering on both sides. Dropping, withdrawing, completing, or deactivating ends it at once everywhere (course pages, submissions, notifications, search, calendar, AI).
- An access check only reads. It must never change data.
- The access rule is written once, in `LmsStudentAccessPolicy`. Every LMS check and list must use it instead of repeating or loosening the conditions.
- Self-service endpoints take the caller from the access token with `AuthenticatedAccount.idFrom(...)`. Never accept an account, student, profile, or enrollment ID from the client to decide whose data is returned.
- `GET /api/v1/lms/my-courses` requires the `STUDENT` role and the `LMS_COURSE_VIEW` permission together. Passing that rule only lets the caller ask; the enrollment policy still decides what is returned.
- LMS read endpoints must be side-effect free.
- `GET /api/v1/lms/courses/{lmsCourseId}` uses the same rule as `my-courses` and runs the access policy again on every request. A missing course and one the student may not use get the same 404, so the API never reveals which LMS course IDs exist.
- `ADMIN` gets no implicit student LMS access. Design any admin or faculty LMS access explicitly, with its own permission.
- A migration that adds a permission also lists it in `docs/permissions.md` and looks roles and permissions up by name, never by ID.
- Do not add historical or read-only LMS access rules without an explicit feature phase.
- Do not add ERP-to-LMS synchronization (listeners, schedulers, startup scans, bulk jobs, or sync records): access is derived, so there is nothing to sync.
- Faculty access must not be modelled from student course enrollment.
- Course content is `LmsCourse` → `LmsModule` → `LmsTopic` in `lms.content`, with `DRAFT`, `PUBLISHED`, `ARCHIVED`. Archive content; never hard-delete it or add delete routes.
- Students see a topic only when the student access policy allows the course and both the module and the topic are `PUBLISHED`. The rule lives in `LmsContentPolicy`; do not repeat or loosen it.
- A course page is an `LmsTopic`; never add a second page model. Students open one at `GET /api/v1/lms/courses/{lmsCourseId}/pages/{pageId}` and faculty preview one, drafts included, at `GET /api/v1/lms/faculty/pages/{pageId}` (course from the stored page); both are answered from exactly what the content routes list, so every hidden page is the same 404. See `docs/course-pages.md`.
- Faculty content changes go through `LmsContentManagementService`, which finds the course from the stored module or topic and checks `LmsFacultyAccessService` every time. Never trust a course ID from the client as ownership. Inaccessible content answers 404.
- Reorder requests must list every non-archived child exactly once; reject duplicates and foreign IDs.
- Study materials (`LmsStudyMaterial`) belong to an `LmsTopic`. MySQL stores only their details; the bytes live in private object storage behind `ObjectStorageService`. Never store file bytes in the database or call the MinIO client outside `common.storage`.
- Object keys are generated by the server (`lms/courses/{id}/topics/{id}/{uuid}`). Never build one from a file name or client input, and never send a key, bucket, storage address, or storage credential to a client. The bucket stays private: no public policies and no public or pre-signed links.
- Students see and download a material only when the student access policy allows the course and the module, topic, and material are all `PUBLISHED`. Faculty manage materials with `LMS_CONTENT_MANAGE` under the faculty access policy; there is no separate material permission.
- Uploads are checked against the allow-list of academic file types, the size limit, the declared type, and the first bytes. Downloads are always attachments. Archive materials and keep their stored files; no hard delete and no file replacement.
- A course has at most one syllabus (`LmsSyllabus` in `lms.syllabus`), always formatted text: faculty save a draft, publishing copies it to the version students read (`firstPublishedAt` kept, `lastPublishedAt` moves), and there is no unpublish or delete. Students read only the published version under the student access policy; faculty change it under the faculty access policy with `LMS_CONTENT_MANAGE`, locking the course row and then reading the syllabus with a locking read (a plain read after earlier queries can see a snapshot from before the lock). Official course details come from the academic records, never the syllabus. See `docs/course-syllabus.md`.
- Learning requirements are a page's `required` flag and a module's `requiresPrevious` flag; the path (locked, complete, progress, next page) is worked out only by `LmsLearningPath`, never stored, and locked modules' text, files, and downloads stay closed. A completion (`LmsPageCompletion`) is one row per course enrollment and page, recorded only by the student's explicit Mark as complete (`LmsPageCompletionService`: visible and open page, enrollment row lock, locking read) and never changed or deleted. Opening a page records nothing. See `docs/learning-progress.md`.
- Course copy (`lms.copy.LmsCourseCopyService`) copies only from an LMS course of the same `Course` in another offering the faculty member taught (an ended teaching assignment counts here and nowhere else), into a course they manage now: modules, pages, study files (bytes to new server-made keys), and the syllabus draft when the target has none, all as drafts after the existing content. Never copy assignments, announcements, submissions, grades, completions, or student data, and never let a copy source grant access to the old course. See `docs/course-copy.md`.
- Course outcomes (`LmsCourseOutcome` in `lms.outcome`) are numbered by the server per LMS course (`CO1`, `CO2`, … under the course row lock and a locking read), never reused, edited only in their plain-text description, and archived, never deleted. `BloomLevel` is optional and decides nothing. An assignment is aligned only through its own alignment route, with active outcomes of its own course (an archived one already aligned may stay). Do not add outcome attainment, program outcomes, or outcome reports without their own phase. See `docs/course-outcomes.md`.
- The question bank (`LmsQuestion` in `lms.question`) belongs to one LMS course; each question keeps its own answers by type (options with the correct ones marked, a true/false answer, accepted short answers, or descriptive guidance), as part of the question. A new or edited question needs review, only a reviewed one may be offered for practice, and every change locks the question row first; questions are archived, never deleted. Routes need `FACULTY`, `FACULTY_COURSE_VIEW`, and `LMS_QUESTION_BANK_MANAGE` under the faculty access policy, finding the course from the stored question. Students have no route to the bank: never send them answers. A question used by a published or archived quiz is never edited (409). See `docs/question-bank.md`.
- Quizzes (`LmsQuiz` in `lms.quiz`) belong to one LMS course and ask bank questions through ordered `LmsQuizQuestion` links with their own marks; nothing is copied from the bank. Questions change only while the quiz is a draft; publishing needs every question active and reviewed (and offered for practice in a practice quiz), records `publishedAt` once, and fixes the questions, type, shuffling, and negative marking. Quizzes are archived, never deleted or unpublished. A bank edit reads the using quizzes with a shared lock before locking the question, and publishing locks the quiz and then reads its questions with a shared lock, so the two never both succeed. Faculty routes need `FACULTY`, `FACULTY_COURSE_VIEW`, and `LMS_QUIZ_MANAGE` under the faculty access policy, finding the course from the stored quiz. See `docs/quizzes.md`.
- A quiz attempt (`LmsQuizAttempt` in `lms.quiz.attempt`) belongs to a published quiz and the student's official `CourseEnrollment`, found with `LmsStudentAccessService.findAccessGrantingEnrollment`; never store or accept an account or profile ID. Its deadline (time limit and closing time) and due date are fixed at the start, and the server's clock decides: answers are taken until the deadline plus a 15-second grace, a hand-in after it is `EXPIRED` at the deadline, and time up is worked out on read, never stored. Starting locks the course enrollment, then the attempts with a locking read (one `IN_PROGRESS` attempt per quiz and enrollment, also by a unique generated column); saving and handing in lock the attempt row. Never send students correct choices, accepted answers, true/false keys, guidance, or explanations. Student routes need `STUDENT`, `LMS_COURSE_VIEW`, and `LMS_QUIZ_TAKE`.
- Quiz marks are worked out on every read by `QuizScoring` (exact choice sets, true/false, normalized short answers, negative marking on wrong objective answers, total never below zero); never store a score. Only a teacher's mark per answer (`LmsQuizAnswerMark`) is stored, replaced without history, for answered questions of handed-in attempts of published quizzes, under the attempt row lock, with the marker and time from the server. Students see a result only once the attempt is handed in, fully marked, and released by the quiz's `resultRelease`; correct answers and explanations only with `showAnswers`, and marking guidance never. Faculty results and marking need `FACULTY`, `FACULTY_COURSE_VIEW`, and `LMS_QUIZ_GRADE`. A quiz mark is an LMS result, not an ERP `CourseResult`.
- Exam blueprints and papers (`lms.paper`) belong to one LMS course and use only active, reviewed questions of its own bank, linked through `LmsExamPaperQuestion` with their own section and marks; nothing is copied from the bank. A blueprint's rows build a draft paper with matching questions chosen at random, never twice, or nothing (409 naming the row). Papers change only as drafts, become `FINAL` once (`finalizedAt` kept), and are archived, never deleted or reopened; a question in a final paper is never edited in the bank (409), with finalizing taking the course row lock, then the paper row, then a shared lock on the questions read only by ID first. The Word document is built per request by `ExamPaperDocument` and never stored. Routes need `FACULTY`, `FACULTY_COURSE_VIEW`, and `LMS_EXAM_PAPER_MANAGE` under the faculty access policy, finding the course from the stored record. Students have no route here. Do not add AI generation or multiple sets without phase 0.14.4. See `docs/exam-papers.md`.
- Rubrics (`LmsRubric` in `lms.assignment.rubric`) belong to one LMS course: 1 to 20 criteria with maximum points and 0 to 6 levels, replaced together on edit, archived never deleted, and kept as they are once used for grading (409). An assignment uses at most one active rubric of its course whose total equals its maximum marks, and its maximum cannot then change. Rubric grading locks the attempt row, then the rubric row alone with a shared lock (an edit takes it alone exclusively first, so the two never deadlock over criteria rows), reads the rubric, refuses with 409 if its stored criteria changed meanwhile, takes points for every criterion once, and saves their sum as the marks through the normal grading rules; the scores (`LmsRubricAssessment`, with each criterion's title and maximum as they were) live with the grade and are removed by a plain regrade. Rubric routes need `FACULTY`, `FACULTY_COURSE_VIEW`, and `LMS_ASSIGNMENT_MANAGE`; rubric grading needs `LMS_ASSIGNMENT_GRADE`. See `docs/rubrics.md`.
- The gradebook (`lms.gradebook`) reads assignment marks (latest attempt's grade) and graded-quiz marks (best fully marked attempt) live through `GradebookBuilder`; never copy or synchronize them. Only manual items (`LmsGradeItem`), their marks (`LmsGradeEntry`, one per item and course enrollment), and a column's one-time `publishedAt` are stored; nothing is deleted or unpublished. Students see only published columns, and quiz attempts only once released. Publishing locks the course row, then reads grade items with a locking read; entering marks locks the item. Faculty routes need `FACULTY`, `FACULTY_COURSE_VIEW`, and `LMS_GRADEBOOK_MANAGE`; `GET /api/v1/lms/courses/{id}/grades` needs `STUDENT`, `LMS_COURSE_VIEW`, and `LMS_GRADE_VIEW`. No weights, percentages, averages, or ranks.
- A course's Files area lists its study materials; a file is always on a page, and there is no second file model. `GET /api/v1/lms/courses/{lmsCourseId}/files` (students, published only) and `GET /api/v1/lms/faculty/courses/{lmsCourseId}/files` (faculty, drafts included) are built from exactly what the content routes list. See `docs/course-files.md`.
- Topic content, announcement messages, and assignment instructions are `PLAIN` or `FORMATTED` (`LmsTextFormat`, a format column beside each text; old texts stay `PLAIN`); every other text, including module and material descriptions, stays plain text. Formatted text is Stacc's small safe set written as Markdown (headings, lists, links, code, tables, KaTeX maths). The server stores it as written and never renders it; the browser shows it only through `FormattedText` (`src/formatting`): HTML skipped, no images, links only through `safeUrl` (https, http, mailto, or a single-slash Stacc path), KaTeX with `trust: false` at 0.18.11 or later. Never add `rehype-raw`, `dangerouslySetInnerHTML`, or another renderer; faculty edit with `FormattedTextField` (Write and Preview). See `docs/text-formatting.md`.
- Announcements (`LmsAnnouncement` in `lms.announcement`) belong to one `LmsCourse`, use `LmsContentStatus`, and are plain or formatted text. Archive them; never hard-delete them or add delete routes.
- `publishedAt` is set by the server on the first publish and never changes. A published announcement may be edited; an archived one can no longer be edited or published.
- Students see only `PUBLISHED` announcements of courses the student access policy allows. Faculty manage them under the faculty access policy, finding the course from the stored announcement. Announcements reuse `LMS_COURSE_VIEW`, `FACULTY_COURSE_VIEW`, and `LMS_CONTENT_MANAGE`; do not add an announcement permission.
- Announcements carry files (`LmsAnnouncementAttachment`, at most 10 listed) through `LmsAttachmentStore` and `LmsAnnouncementAttachmentService`: faculty add and remove them under the faculty access policy with `LMS_CONTENT_MANAGE` (a removed file is kept, never deleted), and students download them only from published announcements of courses the student access policy allows. The first publication notifies the students with access once (`ANNOUNCEMENT_PUBLISHED`), under the announcement row lock. Do not add read receipts, comments, or scheduled publishing without their own phases.
- Assignments (`LmsAssignment` in `lms.assignment`) belong to one `LmsCourse` and store only the definition: title, instructions with their format, `dueAt`, and `maxMarks`. Never put student submissions, marks, grades, or feedback on them.
- `dueAt` is an `Instant` stored in UTC and sent as ISO 8601 with a zone; refuse zone-less times and never assume a time zone. `maxMarks` is `BigDecimal`/`DECIMAL(8,2)`, greater than zero.
- Assignments use `LmsContentStatus` with the same `publishedAt` rules as announcements. Archive them; never hard-delete them. A published assignment stays visible to students after its deadline; never hide or archive it automatically.
- Students see only `PUBLISHED` assignments of courses the student access policy allows. Faculty read them with `FACULTY_COURSE_VIEW` under the faculty access policy, finding the course from the stored assignment; every change also needs `LMS_ASSIGNMENT_MANAGE`.
- Do not add assignment attachments or reminders without their own phase. Only the first publication notifies students, through the Inbox.
- A submission (`lms.assignment.submission`) belongs to one assignment and the student's official `CourseEnrollment`, unique per pair. Never store an account, profile, or login ID on it, and never accept one from the client for "my" submissions: find the enrollment with `LmsStudentAccessService.findAccessGrantingEnrollment`.
- Every hand-in is a new immutable `LmsSubmissionAttempt`. Never edit, overwrite, or delete attempts or their attachments. Reserve attempt numbers under the course enrollment row lock (re-checking it is still `ENROLLED`) and a locking read of the submission, never from `MAX + 1` alone.
- Each attempt keeps `dueAtSnapshot`; `late` is computed from it, never from the assignment's current deadline. Late work is accepted and marked late unless the assignment's submission rules say otherwise.
- Assignment submission rules (`availableFrom`, `allowLateSubmissions`, `availableUntil`, `maxAttempts` on `LmsAssignment`) decide when work is taken, through `submissionWindowAt` and the server's clock; handing in checks the window before storing files and again under the course enrollment and submission locks, where the attempt limit is counted. The due date stays within the opening and closing times. Rules are set only through `PUT /api/v1/lms/faculty/assignments/{id}/submission-rules` (`LMS_ASSIGNMENT_MANAGE`). See `docs/assignment-rules.md`.
- Submission files reuse the study-material file rules and the private bucket behind `ObjectStorageService`, with server-made keys that never reach a client. A student downloads only their own files; anything else answers the same 404 as a missing file. Submission routes need `STUDENT`, `LMS_COURSE_VIEW`, and `LMS_ASSIGNMENT_SUBMIT`.
- A grade (`LmsSubmissionGrade` in `lms.assignment.submission`) belongs to one attempt, at most one each. Regrading replaces the marks and feedback without history. Never put marks on an attempt, submission, or assignment, and never move a grade to another attempt.
- `marksAwarded` is `BigDecimal`/`DECIMAL(8,2)` from 0 to `maxMarksSnapshot`, which is taken from the assignment on the first grading and never changes; never rescale. Feedback is optional plain text up to 10,000 characters, and the server sets `gradedAt`.
- Grading routes need `FACULTY`, `FACULTY_COURSE_VIEW`, and `LMS_ASSIGNMENT_GRADE`, find the course from the stored attempt, submission, or file, and allow only `PUBLISHED` assignments under the faculty access policy; anything else answers 404. Lock the attempt row before creating or replacing its grade.
- Students see each attempt's own grade in their history as soon as it is saved, without the grader. A grade is an LMS assignment result, not an ERP result: do not add GPA, grade history, release steps, late penalties, or new grade notifications without their own phase. The gradebook reads these grades live.
- Faculty LMS access derives directly from official `TeachingAssignment` records through `LmsFacultyAccessService` and the single rule in `LmsFacultyAccessPolicy`. Do not add an `LmsFacultyMembership` without a real need.
- Faculty access needs an `ACTIVE` faculty profile, an `ACTIVE` teaching assignment for the LMS course's offering, and a `DRAFT` or `PUBLISHED` LMS course. Students stay `PUBLISHED`-only; faculty draft access must never reach the student policy.
- `GET /api/v1/lms/faculty/my-courses` requires `FACULTY` and `FACULTY_COURSE_VIEW` together and takes the caller from the access token, never a faculty, profile, employee, or assignment ID from the client. There is no admin pass.
- Faculty create and manage an `LmsCourse` only for an offering they teach through an `ACTIVE` teaching assignment, checked with `FacultyTeachingAccessService` on the offering found from the stored course. `LmsCourseManagementService` owns create, publish, and archive; every route needs `FACULTY`, `FACULTY_COURSE_VIEW`, and `LMS_COURSE_MANAGE`. See `docs/lms-foundation.md`.
- `LmsCourse` stays one-to-one with `CourseOffering` and starts `DRAFT`. Publish only a draft, archive a draft or published course, and never restore, delete, or add course settings fields without their own phase.
- The faculty management list starts from teaching assignments, so offerings without an `LmsCourse` and archived courses always appear. Do not loosen `LmsFacultyAccessPolicy` to show archived courses.
- Faculty never manage course offerings, enrollments, or teaching assignments. Academic data stays the source of truth.
- Course discussions (`lms.discussion`) and messages (`lms.message`) are append-only and never deleted. Course access for both goes only through `LmsCourseParticipation` (student or faculty policy, kind from the route); faculty pin, the asker or faculty accept an answer, and a student sees only their own conversations. Show people by login ID only. Files on records go through `lms.attachment.LmsAttachmentStore`; the feature owns the table and checks every download against its parent. See `docs/course-communication.md`.
- Add LMS content models only in their own feature phases.

## Frontend Authentication

- Sign-in is one form at `/login` with a college ID or employee ID and a password. There is no public signup and no role selector, and the frontend never chooses a role.
- `/login` is the front page with two choices, ERP Login and LMS Login (`?portal=erp` or `?portal=lms`), both opening that same form. The portal only picks the landing page (ERP: Dashboard; LMS: Courses or Teaching for a single-role account, otherwise the Dashboard), never a role or permission. Use Stacc's own name, emblem, and `--color-portal-*` colours; never copy another institution's branding.
- Frontend route guards and stored roles are for the interface only. They are not security: the backend checks every request.
- The frontend never sees or stores the token: it lives in the HttpOnly session cookie. On load `AuthProvider` asks `GET /api/v1/auth/session` once and shows nothing protected while it checks; nothing about the session goes into `localStorage` or `sessionStorage`. Signing out calls the backend and forgets the session whatever the answer. Do not add "remember me" or refresh tokens.
- Never store a password, a signing secret, or any other secret in frontend code or storage.
- `apiClient` sends the cookie (`withCredentials`) and copies the XSRF token; nothing sets an `Authorization` header in the frontend. A 401 on any request except the login and the session check ends the session; a 403 never signs the user out; a failed login is an ordinary form error.
- `/account` (Account settings, in the Account tray) shows the person's own recorded details and official photo, edits only the preferred name and phone, links to Change password, and lists their open sessions from `GET /api/v1/me/sessions` with a confirmed Sign out per other session (`POST /api/v1/me/sessions/{id}/end`, never the current one) and Sign out everywhere. Official photos are JPEG or PNG up to 2 MB, set only by admins (`PersonPhotoService`, audited), stored privately, and shown through the API as image data, never by a storage address.
- When the session says `passwordChangeRequired`, `RequireAuth` shows only the Change password page (`/account/password`), without navigation; Sign out is the only other way on. The page is linked from the Account tray and checks length and matching before sending, but the backend's policy decides.
- Keep one auth path: one `AuthProvider`, one Axios client, one login page.
- Browser calls from another origin are allowed only for the exact origins in `FRONTEND_ORIGIN`, which may send the session cookie. Never use a wildcard. The Docker frontend uses same-origin `/api` through Nginx and needs no CORS.
- Users never select or switch roles. The roles come from the login answer and are read in one place, `src/auth/roles.ts`.
- Support accounts with several roles. Never treat `roles[0]` or any other role as the main one; show every role's section in the fixed order Student, Faculty, Admin.
- Role-aware navigation is for the interface only, never authorization. Every feature must be protected by the backend whether or not its item is visible.
- The navigation is one list in `src/components/navigation/navigation.ts`, shared by the desktop navigation rail (`GlobalNav`, Canvas style: Account tray, Dashboard, one tray per role section named for its work — Academics for `STUDENT`, Teaching for `FACULTY`, Manage for `ADMIN` — then the Common links) and the mobile drawer. Do not create navigation per role, do not repeat shared items for multi-role accounts, and add only features Stacc has.
- Page titles are large, bold, and Stacc navy (`text-3xl font-bold text-portal-navy`). Dashboards show course cards with one steady colour per course (`courseColors.ts`) and upcoming work planner style (`PlannerList`), with only what the API sends.
- An upcoming item is shown as "Soon" and is not a link. Do not create placeholder pages or routes for it.
- Do not build role-specific dashboards or role route trees before their roadmap phases. The student, faculty, and admin dashboards render on `/`, one part per role the account holds, in the fixed order Student, Faculty, Admin; never pick a role with `roles[0]`, and add no role switcher.
- The student Courses page (`/courses`) gets its data only from `GET /api/v1/lms/my-courses` through `apiClient`, grouped by term with one course card each (section and teachers as sent). Never show made-up academic or LMS data, such as teachers, progress, grades, or due dates the API does not send.
- The Courses link is shown to any account holding `STUDENT`. The backend's `LMS_COURSE_VIEW` and enrollment policy still decide what is listed; a 403 shows an access-denied state and never ends the session.
- Read pages must never change data.
- A course page lives at `/courses/:lmsCourseId`, using the `lmsCourseId` from the API. Never put a course code, enrollment ID, or account ID in the URL, and never treat arriving from the list as access: the backend checks every request.
- Every course page shares one course navigation (`CourseNav`: a left column on wide screens, a Course menu on phones) through the nested layout routes `CourseLayout` (Home, Modules, Pages, Assignments, Quizzes, Grades, Announcements, Files, Syllabus, AI Study Assistant) and `TeachingCourseLayout` (Home, Modules, Announcements, Assignments, Rubrics, Quizzes, Gradebook, Outcomes, Question bank, Exam papers, Files, Syllabus, AI Tools). List only sections Stacc has; the navigation is never access control. Course pages start with `PageHeader` and put each part in a `Card` with the shared states (`SectionState`); do not bring back hand-written header or panel class lists. Faculty choose the home (`homeView`: `OVERVIEW`, `MODULES`, `SYLLABUS`) and an optional formatted welcome message through `LmsCourseManagementService.changeHome`; both are LMS settings and never hold official course data. See `docs/course-navigation.md`.
- The course home shows only what `GET /api/v1/lms/courses/{lmsCourseId}` and its `/content`, `/announcements`, and `/assignments` routes return, with each published page as a link to `/courses/:lmsCourseId/pages/:pageId` (text, materials, previous and next). Faculty preview pages at `/teaching/:lmsCourseId/pages/:pageId`; editing stays in course content. The course home's Course tools link to Syllabus (`/courses/:lmsCourseId/syllabus`: official course details, then the published syllabus) and Files; faculty edit the syllabus at `/teaching/:lmsCourseId/syllabus` (Save draft, Publish confirmed first). The course home shows Your progress (required pages completed and Continue) only when there are required pages, pages offer Mark as complete, and faculty set Make required and Wait for previous module in course content. Files are listed at `/courses/:lmsCourseId/files` (searchable, Download) and managed at `/teaching/:lmsCourseId/files` (Upload to a chosen page, Publish, Archive confirmed first, and why a file is hidden). Do not add placeholder tabs or content before their phases.
- Deadlines are entered and shown in the browser's own time zone; "Past due" is display only. The faculty `/assignments` overview links to course pages and is not a second editor.
- The assignment page's submission area shows on time or late exactly as the backend returns it for each attempt, renders submitted text as plain text, and downloads files only through the API.
- Faculty grade at `/teaching/:lmsCourseId/assignments/:assignmentId/submissions`, which shows only what the grading API returns and says that saving makes the grade visible to the student. Grades and feedback are shown per attempt, as plain text.
- On a course page, a 404 shows one "Course unavailable" message for missing and inaccessible courses alike, and a 403 shows access denied without ending the session.
- The faculty Teaching page (`/teaching`) gets its data only from `GET /api/v1/lms/faculty/managed-courses` (grouped by term, with section, enrolled count, and co-teaching as sent; LMS changes refresh `queryKeys.lms.all`), is shown to any account holding `FACULTY`, and shows every offering taught with its LMS state: Create for none, Open and Publish for a draft, Open for a published course, and nothing to open for an archived one. It links only to `/teaching/:lmsCourseId`, never to the student course home. A 403 on faculty pages never ends the session. Do not add invented faculty figures.
- `/teaching/:lmsCourseId` (Home) has Course settings for publishing and archiving, each confirmed when it cannot be undone (archiving returns to `/teaching`), and Course home; modules, announcements, and assignments have their own pages in the course navigation. Do not add student or enrollment editing to faculty pages.
- Content ordering uses keyboard-accessible Move up and Move down buttons. Do not make drag and drop the only way to reorder.
- The ERP pages (academic admin, attendance, results, calendar) are built only from `src/ui` and load data with `useApiQuery`; keep them that way. Admin lists search, filter by status, and page on the client over what the API sent, and a change invalidates `queryKeys.admin.academic`.
- Admins manage accounts at `/admin/users` (Users in the Manage tray), `/admin/users/new`, and `/admin/users/:accountId`; changes that end sessions are confirmed first, and temporary passwords are typed by the admin and never shown again.
- Academic Admin has two rows of `LinkTabs`: areas (Structure, Teaching, People, Calendar; an area's tab opens its first page) and that area's pages. Keep new admin pages inside an area instead of lengthening a row.
- Admins manage the academic masters at `/admin/academic/:section` (departments, programs, sessions, semesters, courses), with Edit but never Delete, and parent selects filled from the admin API.
- Admins manage course offerings at `/admin/academic/offerings`, with a read-only roster at `/admin/academic/offerings/:courseOfferingId/enrollments`, and enrollments at `/admin/academic/enrollments`, one student at a time. It loads one month at a time from `GET /api/v1/calendar/me` with the browser's time zone, lists a multi-day event once with its range, shows Cancelled in words, and adds no data the API does not send. Student deadlines link to the assignment page and teaching deadlines to `/teaching/:lmsCourseId/assignments`; it is not an assignment editor.
- Support is one area per `UserAccount` at `/support`, shown once to any account holding `STUDENT`, `FACULTY`, or `ADMIN`; never build a support area or ticket engine per role, and never use `roles[0]`. ## AI Learning

- AI learning lives in `lms.ai` (backend) and the separate internal `ai-service/` (Python, FastAPI). Spring Boot stays the public API and the only authentication and authorization boundary; the AI service is internal, takes only the shared `X-Stacc-AI-Token`, and is never exposed to browsers or proxied by Nginx. Never send it a user's access token. See `docs/ai-learning.md`.
- AI knowledge comes only from content students can see: `PUBLISHED` topics and study materials under published parents (`LmsContentPolicy`), through `AiKnowledgeSources`. Never index drafts, archived content, announcements, submissions, attachments, grades, feedback, attendance, results, helpdesk, hostel, or campus data.
- Never send the AI service a login ID, profile, account, grade, attendance, result, or any other personal record: only the opaque course key, the content fingerprint, published content, and the question or generation settings.
- MySQL keeps only `ai_course_knowledge_indexes` metadata (status, fingerprint, time, safe last error). Never store vectors, extracted text, prompts, questions, answers, or conversations; AI interactions are stateless.
- Stale is computed from the content fingerprint, never stored. Students need a successful refresh of the current content (`answersFor`); a refresh replaces the index atomically and a failure keeps the previous files.
- Answers must cite retrieved published sources; without a valid citation the result is insufficient context, never general model knowledge. Citations are rebuilt from Stacc's records and never carry storage keys or paths. Treat course text as untrusted: keep the prompt fences and rules, and never request or show hidden reasoning.
- Student routes need `STUDENT`, `LMS_COURSE_VIEW`, and `AI_STUDY_USE` plus `LmsStudentAccessService`; faculty routes need `FACULTY`, `FACULTY_COURSE_VIEW`, and `AI_TEACHING_USE` plus `LmsFacultyAccessService`. No admin pass, and never `roles[0]`.
- Assessment drafts always need faculty review. AI endpoints never create, publish, or grade assignments, and never write results, attendance, or any academic decision; only the normal assignment form creates an assignment, as a draft.
- No commercial AI APIs: providers sit behind `ModelProvider` and `EmbeddingProvider`, with Ollama for real use and the deterministic fake for tests. Tests never need a network, GPU, or model, and no model is downloaded in a build.
- AI is off unless `AI_ENABLED=true`; then failures answer 503 (502 for unusable output) and never affect other features. Do not add chat history, OCR, automatic grading, predictions, rankings, plagiarism detection, or proctoring without their own phase.

## Notifications and Inbox

- Notifications (`com.stacc.backend.notification`) are shared infrastructure for in-app delivery only. It depends on no feature module. See `docs/notifications-inbox.md`.
- `Notification` holds the content once; `NotificationRecipient` holds one account's delivery and read state, unique per notification and account. `readAt` null means unread; do not add a read flag or history.
- Only backend feature services create notifications, through `NotificationService`, in the same transaction as a real change. Never add an endpoint that creates, sends, or deletes notifications, and never take recipients from a client.
- Notify only on real transitions: compare the state before and after, so repeated or no-op calls never notify twice. Resolve recipients with the feature's existing rules (student access policy, calendar relevance, the enrollment's own student), and deduplicate accounts.
- Store only a plain-text title and message, a loose `sourceType`/`sourceId`, and a safe internal `actionPath` (one leading `/`, never `//`, a scheme, or a host). Never copy source records, and never let a source ID or path bypass the destination's own authorization.
- The Inbox is per `UserAccount`, never per role, and never uses `roles[0]`. Its routes need `NOTIFICATION_VIEW` with `STUDENT`, `FACULTY`, or `ADMIN` and take the account from the token; another account's row answers 404. There is no deletion.
- The frontend has one `/inbox` page and one shared unread count for the navigation badge and the bell. Loading the Inbox marks nothing read, and there is no polling. Do not add SMS, push, WebSocket, Server-Sent Events, Kafka, or Redis without their own phase.
- Each person chooses per category (`NotificationCategory`) whether notifications reach the Inbox and whether they are emailed at once or in a daily digest (`/inbox/settings`, `NOTIFICATION_VIEW`). Email is off unless `MAIL_ENABLED=true`, goes only after commit to the college-recorded address of an `ACTIVE` account, is plain text with a link from `MAIL_LINK_BASE_URL`, and never stores or logs an address or content. The digest marks its rows sent under a row lock before sending. See `docs/notification-settings.md`.

## Helpdesk

- Stacc has one helpdesk ticket engine, `support.helpdesk`, for every kind of issue. Kinds are configurable `HelpdeskCategory` rows, never an enum; do not build a ticket engine per module. See `docs/helpdesk.md`.
- Category codes are unique, uppercase, and fixed after creation. Make a category inactive instead of deleting it; an inactive category keeps its tickets but takes no new ones.
- The requester, every author, and every actor come from the access token; never accept an account, requester, author, or actor ID from a client. Ticket numbers (`STC-%06d`), `resolvedAt`, and `closedAt` are set by the server.
- Requesters choose `LOW`, `NORMAL`, or `HIGH`; only the support team sets `URGENT`. Only active accounts holding `ADMIN` can be assigned, and `GET /api/v1/helpdesk/admin/assignees` lists exactly those, by login ID only.
- Statuses: `OPEN` to `IN_PROGRESS`, `WAITING_ON_REQUESTER`, `RESOLVED`, or `CLOSED`; `IN_PROGRESS` to `WAITING_ON_REQUESTER`, `RESOLVED`, or `CLOSED`; `WAITING_ON_REQUESTER` to `IN_PROGRESS`, `RESOLVED`, or `CLOSED`; `RESOLVED` to `CLOSED`. The same value is a no-op; anything else is 409. Only the requester's reply moves a waiting ticket back to `IN_PROGRESS`, and only the requester reopens a `RESOLVED` ticket, within 7 days. A `CLOSED` ticket refuses every change and never reopens. Any other reply never changes the status.
- Messages and history are append-only. Write history only for real changes, through the command service's single recorder, and lock the ticket row before every change. Never add delete routes for tickets, messages, history, or categories.
- Access is decided once, in `HelpdeskAccessService`: own tickets need the `_OWN` permissions; every ticket needs `ADMIN` with the `_ALL` permissions, and changes `ADMIN` with `HELPDESK_TICKET_MANAGE`. The role alone is no pass. A ticket the caller may not see answers the same 404 as a missing one.
- Admin replies, real status changes, and assignments notify through `HelpdeskNotifications` and the Inbox, never the actor themselves, linking to `/support/tickets/{ticketId}`. Do not rewrite old notification rows.
- Support teams (`HelpdeskTeam`, made inactive never deleted) take the tickets of the categories routed to them; their members (admins or staff with `HELPDESK_TEAM_WORK`) work only their teams' tickets, decided by `HelpdeskAccessService.worksOnTeam`. Internal notes are seen only by the support side and notify nobody. Ratings are given once by the requester; `firstResponseAt` is set once by the first visible support reply. See `docs/helpdesk.md`.
- Do not add SMS, push, SLAs or escalation, or helpdesk analytics without their own phase.

## Approval Workflow Engine

- The approval engine (`com.stacc.backend.approval`) is shared infrastructure, one for all of Stacc. Business modules own their records, forms, eligibility, and pages; never build an approval engine per module. See `docs/approval-workflow.md`.
- Never expose a public route to start or cancel an approval request. Modules call `ApprovalWorkflowService.startApproval` and `cancelApproval` with the requester they authenticated; the engine stores only `sourceType`, `sourceId`, and a subject, never business payloads, JSON, or attachments, and never changes the business record.
- Workflows are ordered, sequential, role-based steps (1 to 10), each naming an existing `Role` that holds `APPROVAL_TASK_DECIDE`, never an account. Codes are uppercase and fixed; deactivate workflows instead of deleting them.
- A request copies its workflow's steps when it starts; editing a workflow affects future requests only. A PENDING request has exactly one PENDING step and `currentStepOrder` pointing at it.
- A step is decided only by an account with `APPROVAL_TASK_DECIDE` that holds the step's role in its token and in the database and is not the requester. There is no admin pass, and never use `roles[0]`.
- A step may also name an `ApproverRelationship` (such as `STUDENT_DEPARTMENT_HEAD` with `HOD`), resolved once at start through the owning module's `ApproverRelationshipResolver` to one assigned account; then only that account decides it, and it alone sees and is notified of the task. No approver found means nothing starts (409). Never resolve a relationship again or let the engine import a business module.
- Rejecting needs a comment, rejects the request, and skips later steps. Finished requests never change; deciding an already decided step answers 409. Lock the request row before every decision or cancellation.
- History is append-only and written only by the engine's single recorder. Notifications go to the step's role holders and the requester, with no link until a module adds pages.
- Do not add parallel or conditional steps, quorum, delegation, escalation, deadlines, attachments, form builders, or a generic approval UI without their own phase.

## Hostel

- Hostel (`com.stacc.backend.hostel`) is the first real business consumer of the approval engine. Approval state always comes from the linked `ApprovalRequest`: never add a status column to `HostelApplication`, never change approval tables from Hostel, and decide only through the approval task routes. `HOSTEL_MANAGE` is no approval pass. See `docs/hostel-management.md`.
- Applications use the `HOSTEL_APPLICATION` workflow by code (reference data from `V53`, one ADMIN step). Apply and cancel through `ApprovalWorkflowService`; the student always comes from the token.
- A student applies only for a session with an ENROLLED semester enrollment and an ACTIVE profile; no LMS data is needed. One PENDING or APPROVED application per student and session; rejected or cancelled ones allow reapplying. Only pending applications without an active allocation can be cancelled.
- Students never choose a hostel, room, or bed. Only APPROVED applications are allocated, by an admin from the token.
- Occupancy is derived from ACTIVE `HostelAllocation`s; never store an occupied flag or room capacity. A bed, an application, and a student each have at most one ACTIVE allocation, enforced under the fixed lock order student, application, hostel and room (shared), bed.
- Vacating keeps history and allows reallocation. Never hard-delete hostels, rooms, beds, applications, or allocations. Do not deactivate what holds an active allocation, and fix room and bed numbers once they have allocation history.
- Wardens are `HostelWarden` assignments (hostel, optional block; ended, never deleted); `HostelWardenService.isWardenOf` alone decides a warden's access (`WARDEN` with `HOSTEL_WARDEN_VIEW`), and other hostels answer 404. A student's preference is a wish only. Beds under maintenance take no allocation and an occupied bed cannot go under maintenance. Occupancy, bed maps, and queue positions are worked out live, never stored. See `docs/hostel-management.md`.
- Do not invent gender or other eligibility attributes. Do not add payments, mess, visitors, or campus services without their own phase. Never use `roles[0]`.

## Passes, Outings, and the Gate

- Every pass goes through the one `pass.PassService`: a random code shown once to its holder, only its SHA-256 fingerprint stored, a time window, one purpose and source, revoked never deleted; a new pass for a source revokes the old ones. Never store or log a code. See `docs/passes-and-gate.md`.
- Hostel outings (gate passes and leave, and leave extensions) are approved only through the `HOSTEL_OUTING` workflow by the student's hostel warden; never copy approval state. The gate's movement log is append-only and decides whether a student is outside; overdue is worked out on read. Security (`SECURITY` with `GATE_PASS_VERIFY`) only checks codes, records movements, and looks students up.
- Hostel complaints are ordinary helpdesk tickets of the `HOSTEL` category with the room attached; never build a second ticket engine.

## Campus Services and Notices

- Campus (`com.stacc.backend.campus`) has a service catalog, service requests, and notices. A campus service request is not a helpdesk ticket: never add messages, replies, or attachments to it; conversations belong to Support. See `docs/campus-services.md`.
- `CampusServiceDefinition`s are configurable data, never an enum. Codes are uppercase, unique, and fixed after creation; services are made inactive, never deleted. A service is offered to `STUDENT`, `FACULTY`, or both and is matched against every role the account holds. No dynamic forms: requests are a subject and plain-text details.
- A service that needs approval names an approval workflow by code, checked with `ApprovalQueryService.isStartableWorkflow` when the setting changes and again on every new request (409 otherwise). Approval settings affect future requests only.
- Requests with approval start `SUBMITTED` and start the engine with source type `CAMPUS_SERVICE_REQUEST`; requests without approval start `APPROVED` (accepted for handling). The requester always comes from the token.
- Never duplicate the approval state machine or write approval tables from Campus. While a request is `SUBMITTED`, show the status derived from its approval; store it only through `CampusServiceRequestService.synchronize` under the row lock. Cancel pending approvals with `cancelApprovalIfPending`, never by reading the status first. Decisions go only through the approval task routes; `CAMPUS_SERVICE_MANAGE` is no approval pass.
- Only `SUBMITTED` or `APPROVED` requests can be cancelled, and only `APPROVED` ones completed (once, with `completedAt`). Never delete requests.
- Notices are `DRAFT`, `PUBLISHED`, `ARCHIVED`, plain text, and visible to at least one role. `publishedAt` is set on the first publication only; archived notices are final and read-only. The feed matches any role the account holds and lists each notice once; never use `roles[0]`. No delete, restore, scheduling, expiry, comments, or attachments.
- Only a notice's first publication (to active accounts of its roles, deduplicated) and a completed request (to its requester) notify, through `CampusNotifications`. Do not repeat the engine's approval notifications.
- Do not build transport, library, ID-card inventory, or other domain subsystems inside the catalog without their own phase.

## Search

- Global search (`com.stacc.backend.search`) composes read-only providers; it owns no data and no access rule. Each provider reuses its domain's access services (`LmsStudentCourseQueryService`, `LmsFacultyCourseQueryService`, `LmsFacultyManagedCourseQueryService`, the calendar scopes, `HelpdeskAccessService`) and requires the same role and permission as the domain's own routes. A text match never grants access. See `docs/search.md`.
- `GLOBAL_SEARCH_USE` only allows using search and never replaces a feature permission. A kind the account may not see is left out (an empty page on `/api/v1/search/results`), never 403 or 404, and is never counted. Counts use exactly the item query's conditions.
- The searcher always comes from the access token. Never accept an account, student, faculty, profile, or enrollment ID in a search request, and never use `roles[0]`: check every role the account holds.

- Student and teaching results are separate kinds with different pages; deduplicate by record within a kind (a notice or event appears once for a multi-role account), never across workflows.
